### [0:00 — PROBLEM — 40s]

> Every blockchain game today has the same dirty secret: the fun parts — generating content, evaluating player actions, updating game state — all run on a centralized server. The smart contract is just a scoreboard. One server goes down, one company pulls the plug, and the game is gone forever.

> There's a deeper problem: who decides if your answer is right? A backend you can't audit. An API you have to trust. And when a game uses AI to generate content — who controls the prompt? Who verifies the output? That's not Web3 — that's Web2 with a wallet.

> We asked ourselves: what if the AI itself ran inside a decentralized oracle network? What if every LLM call, every game decision, every piece of content was generated by consensus — not by a server?

---

### [0:40 — SOLUTION + ARCHITECTURE — 40s]
*(show architecture diagram or GitHub repo)*

> Carmen Sandiego On-Chain is a fully decentralized mystery game. The entire game brain — 6 independent workflows — runs on Chainlink CRE, the Compute Runtime Environment.

> Here's how it works: each workflow is written in TypeScript, compiled to WebAssembly, and executed inside every node of the Chainlink DON — the Decentralized Oracle Network. All nodes run the same WASM bytecode, produce the same output, and reach consensus. The result is signed with a threshold ECDSA signature and delivered on-chain through the Keystone Forwarder.

> No backend. No admin key. No single point of failure. The game logic is decentralized down to the AI calls.

> The stack: Chainlink CRE for compute, VRF v2.5 for randomness, Data Feeds for real-time prices, and smart contracts on Sepolia with commit-reveal cryptography.

---

### [1:20 — CRE DEEP DIVE: THE CODE — 70s]
*(show `generate-briefing/main.ts` in VSCode)*

> Let me walk you through the most complex workflow: generate-briefing. This single TypeScript file compiles to WASM and runs inside the DON. Watch what happens in one execution.

> First, the trigger. This workflow fires on a `MissionStarted` event — a LogTrigger capability. When a player starts a mission on-chain, the DON picks it up automatically.

> **Line 453** — the workflow reads the Chainlink ETH/USD Data Feed using `EVMClient.callContract`. Not an HTTP request to an API — a direct on-chain read from inside the WASM sandbox. The price, round number, and timestamp are all verifiable. This proves CRE workflows can consume live blockchain data as part of their computation.

> **Line 558** — here's where it gets interesting. The workflow calls the Groq API with LLaMA 3.3-70b using `CRE HTTPClient.sendRequest().result()`. This is an AI model call happening inside a decentralized computation. Temperature is set to zero — that's critical. Zero temperature means deterministic output, so all DON nodes generate the exact same briefing and reach consensus.

> The prompt is crafted from on-chain data: the mission scenario, the target city, the player's history. The AI generates a noir-style intelligence briefing unique to this mission.

> **Line 595** — the generated briefing is encrypted with ECIES using the player's secp256k1 public key, which was registered on-chain during player setup. The encryption uses `@noble/curves v1.x` — specifically pinned because v2.x breaks the CRE WASM compiler. After encryption, not even the DON nodes can read the briefing. Only the player with the matching private key in their browser can decrypt it.

> **Line 611** — `writeReport` packages the encrypted briefing into a signed CRE report and delivers it through the Keystone Forwarder. The smart contract — `GameMasterProxy` — verifies the DON's threshold signature before accepting the data. If the signature doesn't match, the transaction reverts. Zero trust required.

> So in one workflow execution: live blockchain data + AI generation + end-to-end encryption + on-chain delivery. All inside WASM. All decentralized.

### [2:30 — THE 6 WORKFLOWS — 60s]
*(quick tour in VSCode, show each main.ts briefly)*

> The game runs on 6 independent CRE workflows. Each compiles to its own WASM module — no shared state, no cross-workflow imports.

> **1. carmen-moves** — a CronCapability workflow, triggered every 3 minutes. It reads all active missions, brute-forces Carmen's current location from the commit-reveal hash, picks a new city using targetHash entropy, and updates the on-chain target. This creates real time pressure — Carmen is always moving.

> **2. generate-briefing** — we just saw this one. LogTrigger on `MissionStarted`. Reads on-chain state, calls Groq LLaMA for the briefing, encrypts with ECIES, delivers via signed report.

> **3. mission-start** — the core clue engine. Triggered by `InvestigationSubmitted` events. When a player investigates a city, this workflow brute-forces Carmen's actual location from the salt, determines if the guess was correct, selects a true or false clue from the scenario pool, calculates a deterministic strength score — 40 to 95 for correct, 20 to 55 for wrong — and if strength exceeds 65, generates an encrypted wallet fragment as evidence. When the player finds the right city with enough clues, this same workflow triggers the capture and NFT minting. All without the smart contract ever knowing Carmen's location in plaintext.

> **4. generate-finale** — triggered by `CarmenCaptured`. Builds an SVG trophy entirely in TypeScript — gradient fills, tier colors, mission stats — encodes it as a base64 data URI, generates an ERC-721 metadata JSON, and delivers it via `ACTION_SET_TOKEN_URI`. The NFT is fully on-chain — no IPFS, no external hosting. It also generates a victory narrative using Groq LLaMA or falls back to an enriched template.

> **5. player-registration** — gasless onboarding. Triggered by `RegistrationRequested`. Validates nickname availability and registers the player on-chain.

> **6. player-check** — triggered by `PlayerCheckRequested`. Verifies player status for the frontend.

> Let me summarize the AI integration flow. When a player acts on-chain, an event fires. The DON detects it via LogTrigger. Every node compiles and runs the same WASM. ## CRE Technical Details (for Q&A / judges)

| Topic | Detail |
|---|---|
| **WASM compilation** | TypeScript → WASM via CRE CLI bundler; each workflow is self-contained |
| **Determinism** | Temperature=0 on LLM calls; all DON nodes produce identical output |
| **Consensus** | Threshold ECDSA signature; majority of nodes must agree on result |
| **Capabilities used** | EVMClient (on-chain reads), HTTPClient (Groq API), writeReport (on-chain writes), CronCapability (scheduling), LogTrigger (event-driven) |
| **WASM constraints** | No async/await in CRE v1; synchronous `.result()` pattern; @noble v1.x only |
| **Security model** | ECIES secp256k1 encryption; commit-reveal hash; sandbox isolation |
| **Fallback strategy** | AI calls have enriched-template fallback if LLM fails — game never breaks |
| **Networks** | Sepolia (HQ), Arbitrum Sepolia (Tokyo), Base Sepolia (Paris), XDC Apothem (London) |
